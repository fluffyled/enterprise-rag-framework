# Комплексный бенчмарк для иерархического RAG: 50 сложных вопросов

Создан из `raw.zip`, предоставленного пользователем, для проверки не только нахождения документа, но и восстановления всей процедуры из нескольких пунктов.

## Что внутри

- `hierarchical_complex_qa_50.jsonl`: основная машинная gold-разметка — вопрос, полный эталонный ответ, `required_facts`, `gold_evidence`, координаты, `split`, тип вопроса.
- `hierarchical_complex_qa_50.csv`: плоская таблица для просмотра вопросов и источников.
- `hierarchical_complex_qa_50.xlsx`: четыре листа: **Обзор / Вопросы / Шаги ответа / Источники**.
- `required_facts.csv`: каждый обязательный факт отдельно, с `evidence_id`.
- `gold_evidence_units.csv`: полные дословные цитаты и место в исходном документе.
- `dataset_stats.json`: проверяемая сводка.
- `validate_dataset.py`: повторно сравнивает все сохранённые текстовые диапазоны с `raw.zip`.
- `evaluate_hierarchical.py`: оценка retrieval / покрытия evidence по предсказаниям поисковика.
- `AGENT_IMPLEMENTATION_PLAN.md`: подробное техническое задание агенту.

## Состав набора

- **50 вопросов** — 15 dev и 35 test; все отвечаемые.
- **224 обязательных элемента ответа** (шаги, сроки, ограничения, участники, исключения).
- **167 уникальных точных фрагментов** (пунктов PDF / абзацев DOCX).
- **91 уникальная source unit** (PDF-страница или DOCX-абзац).
- **8 документов** с доступным текстом, из них 3 вопроса требуют сразу два документа.
- Типы: процедуры, условные случаи, развилки, сравнения, распределение ролей, междокументный поиск.

**Точность:** скрипт проверил, что все сохранённые цитаты являются точными подстроками извлечённого текста исходных файлов, с совпадающими хешами source-unit. Это механическая проверка происхождения доказательств; она **не является независимой экспертной юридической или содержательной валидацией каждой формулировки ответа**. В вопросах есть редакционно составленные обобщения, поэтому перед использованием в финальном high-stakes тесте желательно выборочно просмотреть их специалистом по документам. Сканы без доступного текстового слоя и XLSX в этот набор не включались.

### Координаты источников

- PDF: физическая `page`, отсчёт с **1**. `section` — номер пункта, извлечённый из страницы. Пункт может переходить на следующую страницу: тогда цитата помечена `продолжение`.
- DOCX: `paragraph` отсчитывается с **1** (совместим с прежним gold dataset), `paragraph_zero_based` — индекс `python-docx` для программного доступа.
- `location.start`, `location.end` — символьные смещения в тексте конкретной PDF-страницы, извлечённой через `fitz.get_text(sort=True)`, или в строке абзаца DOCX, с полуоткрытым интервалом `[start,end)`.
- `source_unit_id` и `evidence_id` — **benchmark-идентификаторы**, не существующие автоматически в поисковом индексе проекта. Для использования построить маппинг индексного чанка на документ/страницу/абзац/пункт.
- `parent_group_hint` — только эвристическая подсказка (например, для `3.4` родительским может быть раздел `3`). **Не считать точной разметкой реальных `parent_id` в проекте.**

## Пример полей одной строки JSONL

```json
{
  "id": "HQ001",
  "question": "У сотрудника перестал работать служебный компьютер...",
  "reference_answer": "1. ...\\n2. ...",
  "required_facts": [
    {"fact_id": "F01", "text": "...", "evidence_ids": ["IT_p2_3_1"]}
  ],
  "gold_document_filenames": ["Приказ и Регламент работы первой линии техподдержки.pdf"],
  "gold_source_unit_ids": ["IT::pdf_page::2"],
  "gold_clause_ids": ["IT_p2_3_1"],
  "answerable": true,
  "split": "test"
}
```

Это иллюстрация схемы: полные значения находятся в `jsonl`.

## Как проверить цитаты

Установить зависимости `pymupdf`, `python-docx` и выполнить:

```bash
python validate_dataset.py --raw-zip path/to/raw.zip
```

Скрипт заново извлечёт native-text, проверит хеш unit и точные позиции цитат. **Без OCR.**

## Как оценить retrieval и selection

Подготовить JSONL, где каждая строка содержит predictions для вопроса:

```json
{"id":"HQ001","retrieved_documents":["Приказ и Регламент работы первой линии техподдержки.pdf"],"retrieved_source_units":["IT::pdf_page::2","IT::pdf_page::3"],"selected_context_clause_ids":["IT_p2_3_1","IT_p2_2_1","IT_p3_4_1","IT_p3_4_2","IT_p3_3_4"]}
```

Порядок в `retrieved_*` — порядок ранжирования; `selected_context_clause_ids` — доказательства, фактически попавшие в контекст LLM. Это пример формата, не результат реального запуска retrieval.

```bash
python evaluate_hierarchical.py --gold hierarchical_complex_qa_50.jsonl --predictions predictions.jsonl --split test --out metrics.json
```

Метрики: Document/Source-unit Recall@1/5/10, Clause Recall@1/5/10 (если передаются retrieved clause IDs), доля вопросов с полным документным/юнитным покрытием, `selected_clause_coverage`, `fact_evidence_coverage`. Системе нужно возвращать **точные идентификаторы clause или делать отдельный маппинг на них**. Наличие страницы само по себе не доказывает попадание всех пунктов в текст LLM.

Оценка фактического `Procedure Step Recall`, неверных шагов, галлюцинаций и цитирования требует отдельных предсказанных ответов и judge/manual разметки. Скрипт retrieval их **не подменяет**.

## Как безопасно использовать dev/test

На `dev` выбрать стратегию и параметры расширения. Затем зафиксировать конфигурацию и сравнить на `test`: `BGE baseline`, `BGE + parent`, `BGE + related sections`, `BGE + adaptive expansion`. Дополнительно запустить старый `rag100` для регрессионной проверки однофактных вопросов. Не вводить hard-coded branch по ID бенчмарка в runtime.

**Область применимости:** все вопросы complex50 отвечаемые. Для оценки отказов на вопросах без подтверждения использовать неотвечаемые вопросы старого `rag100` или добавить отдельный вручную проверенный negative-set; не приписывать complex50 метрику abstention.
