# ТЗ для ИИ-агента: Hierarchical RAG / Parent–Child / восстановление процедур

## 0. Что уже известно и что надо сохранить

Проект индексирует регламенты, выполняет семантический поиск и передаёт выбранные чанки в LLM. На `rag100` вариант `BGE-M3 E2` показал лучшие показатели ранжирования среди проверенных: Document Hit@5 = 1.000, Source-unit Hit@1 = 0.797, Source-unit MRR = 0.858 на 74 отвечаемых тестовых вопросах. При этом coverage снижал Source-unit Hit@1 на однофактных вопросах. Это **предварительные результаты retrieval**, не доказательство качества готового ответа.

**Задача новой итерации:** найти точные чанки по BGE-M3, восстановить из структуры документа *целые логические единицы* (пункт, подраздел, связанные положения), отобрать достаточный контекст под token budget и сформировать обоснованный пошаговый ответ. Не заменять существующий поиск; внедрять через отдельный режим конфигурации.

**Не считать реализованными** перечисленные ниже новые компоненты: сначала изучить фактические исходники и сохранить воспроизводимые результаты старых конфигураций. Пути `data/rag100/`, `scripts/evaluate_rag100.py` и `reports/retrieval_v3/...` — ориентиры из предыдущего исследования; проверить наличие в актуальной ветке.

## 1. Неприкосновенные условия

1. Никаких специальных правил под конкретные вопросы из gold QA, названия документов или известные ответы. Gold-разметку видеть только в offline evaluation; runtime не должен считывать её.
2. Сохранить baseline E5 и BGE-M3 и их параметры. Не ломать существующие API, индексацию и интерфейс генератора.
3. На test не подбирать длину разделов, `top_k`, коэффициенты, пороги или prompt. Настраивать на dev, фиксировать параметры, затем запускать test единожды для выбранных гипотез.
4. Сравнивать варианты при одинаковом доступном бюджете токенов и одинаковой LLM (отдельно разрешить quality-vs-budget curve).
5. Сохранять оригинальные идентификаторы документа, путь, страницу PDF, индекс абзаца DOCX, номер пункта, ссылки на родительский блок, диапазоны символов и хеш исходного текста.
6. При конфликте/устаревании документов не выбирать норму произвольно: фиксировать дату/версию и сигнализировать о противоречии.
7. Система не должна выдумывать недостающие шаги или содержимое раздела, которого нет в доступных документах.

## 2. Итерация A — быстрый эксперимент *без переиндексации*

**Цель:** проверить гипотезу Parent Expansion на текущем BGE-M3 до масштабного рефакторинга ingestion.

1. Изучить текущие цепочки `ingest → chunk → embedding/index → retrieve → selection → prompt → generation` и места, где хранятся `document_id`, `source`, `page`, `paragraph`, `chunk_id`.
2. Построить sidecar-хранилище разделов для восьми текстовых документов benchmark (с поддержкой расширения на весь корпус). В первую очередь использовать нумерованные пункты/подпункты, а не произвольные соседние предложения.
3. Для каждого индексного чанка вычислить привязку к минимальному соответствующему **логически завершённому родительскому блоку**. Сохранять `chunk_id → parent_id` и возможность получить `parent_text` целиком.
4. Реализовать `expand_to_parent(retrieved_chunks, mode='section')`: dedup по `parent_id`, выводить полный родительский пункт вместе с заголовком, оговорками и внутренними списками. Не использовать объёмную главу, когда пункт достаточен.
5. Если пункт длиннее допустимого бюджета, выбрать релевантные связанные подпункты, но **не обрезать без отметки** условие/исключение посреди предложения или списка.
6. Добавить trace для каждого блока: исходные hit-чанки, их score/rank, выбранный parent_id, сколько токенов добавлено, какие пункты не поместились.

**Варианты A/B:** `BGE-M3 E2 (baseline)`, `BGE-M3 E2 + fixed parent section`, `BGE-M3 E2 + adaptive parent`. Пока без reranker и LLM-based query router: требуется проверить изолированный эффект расширения.

**Definition of Done:** для найденного чанка можно детерминированно получить полный пункт, provenance не потерян, повторные попадания не дублируют контекст; есть тест на многостраничный пункт.

## 3. Итерация B — структурный разбор PDF и DOCX

**Цель:** гарантировать, что parent действительно является смысловым пунктом, а не очередным пакетом в 2000 символов.

### Промежуточная модель

```json
{
  "document_id": "stable-document-id",
  "document_version": "content-sha256",
  "node_id": "document-id::s3.1::p3.1.2",
  "node_type": "document|section|subsection|clause|paragraph|list|table",
  "parent_id": "document-id::s3.1",
  "section_path": ["3", "3.1", "3.1.2"],
  "heading": "Порядок оформления",
  "text": "Полный текст логической единицы",
  "span": {"page_start": 12, "page_end": 13, "paragraph_start": null},
  "references": ["5.4", "Приложение 2"],
  "children_ids": [],
  "source_sha256": "..."
}
```

1. Для PDF извлекать страницы, текстовые блоки, заголовки и нумерацию; научиться соединять пункты, пересекающие границы страниц. Проводить sanity-check на PDF без текстового слоя: не подменять распознавание сканов пустыми разделами.
2. Для DOCX использовать нумерацию/стили, фактические абзацы и таблицы; **не терять таблицы, списки и вложенные маркеры**. Стабилизировать 0-based/1-based нумерацию абзацев: benchmark хранит 1-based и дополнительно `paragraph_zero_based`.
3. Учитывать пункт «3.1» с подпунктами «3.1.1» и т. д., а также документы с простой сквозной нумерацией «46.», «47.» и разделами без номера.
4. Разделять блоки на `leaf_chunk` для поиска и `parent_node` для восстановления контекста. Не дублировать полный раздел в embedding каждого leaf по умолчанию.
5. Валидировать восстановление: текст родительского раздела должен покрывать все принадлежащие ему дочерние предложения **без потери и перестановки**; строгий unit-тест на границы, ссылки, нумерованные списки и таблицы.
6. Добавить cross-reference graph: из `п. 14`, `согласно приложению № 7` и подобных ссылок получать кандидаты связанные пункты. Не путать ссылку на внешний приказ с доступным внутри корпуса документом.
7. Отдельно логировать confidence parser'а; при неопределённой структуре — fallback к соседним абзацам с ограничением и сохранённой исходной страницей.

**Definition of Done:** reproducible `document_tree.jsonl` / storage, stable IDs, child-parent maps, traceable provenance, контроль корректности на выбранных документах.

## 4. Итерация C — адаптивная глубина контекста

**Три режима:**

- `precise`: точный пункт + необходимое исключение / определение; для однофактных вопросов.
- `section`: целый подпункт или небольшой раздел + прямые ссылки; для «как оформить», «кто и когда».
- `procedure`: несколько тематически связанных пунктов/подразделов; для полного алгоритма действий, условий и развилок.

### Pipeline

```text
query
  → BGE-M3 candidate retrieval (leaf chunks)
  → source-aware aggregation by parent_id
  → question intent / procedure-vs-fact classification
  → section candidates + referenced sibling/exception nodes
  → evidence coverage, relevance and redundancy selection
  → token budget packing with provenance
  → LLM generation with step→citation mapping
```

### Правила проектирования

1. Не выбирать режим `procedure` просто по наличию слова «как»; сначала попробовать прозрачный router на признаках вопроса (срок, список условий, несколько самостоятельных требований). Если classifier ошибается, использовать relevance-first fallback.
2. Защитить наиболее релевантный пункт от удаления: сохранять `top_p` кандидатов по релевантности, затем добавлять связанные блоки, которые увеличивают **маржинальное покрытие** требований.
3. Оценивать `score(node) = α·relevance + β·marginal_coverage − γ·redundancy − δ·token_cost`. Компоненты нормализовать, параметры подбирать только на dev.
4. Соседний пункт включать только при правдоподобной связи: вложенный список, явная текстовая ссылка, переход/исключение, последовательные шаги одной процедуры.
5. В выдаче хранить **ранжирование найденных leaf**, **ранжирование parent**, и **итоговый порядок доказательств** отдельно. Не отождествлять Hit@K по чанкам с Hit@K по финальному контексту.
6. Задать бюджеты (пример стартовой сетки, не финальное значение): `leaf_top_k ∈ {10,20,30}`, `max_context_tokens ∈ {2500,4000,6000}`, `protected_top_p ∈ {1,2}`. Сетка — только dev; при равном качестве предпочесть меньшее время и меньше токенов.

## 5. Итерация D — генерация полноценной инструкции

Передавать не поток предложений, а структурированные evidence blocks:

```text
[Источник: Файл.pdf, стр. 13, пункт 53, evidence_id=...]
<полный текст пункта 53>
[Источник: Файл.pdf, стр. 14, пункт 65, evidence_id=...]
<полный текст пункта 65>
```

Промпт генератора:

1. Сначала определить, есть ли подтверждённый ответ в предоставленных блоках. Если данных недостаточно — указать недостающую часть, не выдумывать её.
2. Составить **полную и упорядоченную** процедуру в пунктах: кто выполняет, действие, срок, входной документ, результат.
3. Отдельно вывести условия/исключения и развилки («если …, то …»).
4. Для каждого существенного шага дать ссылку `имя документа + страница/пункт` по переданному provenance. Не писать фиктивные ссылки.
5. Не выдавать нормативы планирования за нормы фактической компенсации; различать действия из разных редакций документов.
6. При конфликте документов показывать обе нормы, даты и предупреждение; не разрешать конфликт автоматически без утверждённого policy.

**Не нужен** LLM reranker на первом эксперименте. Reranking — отдельная последующая абляция, если ошибка именно в порядке retrieved-родителей.

## 6. Итерация E — методология тестирования

### Датасеты

- `rag100`: короткие факты и точность поиска — регрессионный контроль.
- `hierarchical_complex_qa_50.jsonl`: 50 новых сложных вопросов на основе исходных документов; 15 dev и 35 test. В каждом вопросе 2–6+ обязательных пунктов ответа и несколько точных подтверждений.
- CUAD / MultiDoc2Dial: переносимость на другие типы текстов, с учётом фактического наличия этих бенчмарков в репозитории.

### Метрики retrieval / context

- `Document Recall@K`, `All-Gold-Documents@K`, `MRR` (если есть релевантный один документ).
- `Source-unit Recall@K`, `Source-unit MRR` (PDF-страница / DOCX-абзац), отдельно для retrieval и selected context.
- `Clause Recall@K`: по точным пунктам; на одной PDF-странице могут быть 2+ разных gold-пункта, поэтому page recall не заменяет clause recall.
- `Evidence Coverage@budget = найденные gold-пункты / все gold-пункты`, микро и макро.
- `Fact Evidence Coverage = доля обязательных шагов, для которых все необходимые evidence есть в итоговом контексте`.
- `Context Precision = доля переданных токенов, относящихся к полезным evidence` (на размеченном подмножестве; не вычислять из gold без выравнивания).
- `Token Cost`, latency p50/p95, peak VRAM, throughput.

### Метрики генерации

- `Procedure Step Recall`: доля обязательных фактов, корректно отражённых в ответе (взвешивание по шагам, не по буквальному overlap).
- `Procedure Complete@all`: все обязательные шаги, условия и сроки присутствуют.
- `Unsupported Step Rate`: доля недоказанных утверждений/действий.
- `Step-level Citation Accuracy`: правильно указан источник каждого шага.
- `Conditional Accuracy`: модель верно различает ветви «если/иначе».
- `Abstention Accuracy`: отдельно на отрицательных вопросах `rag100`; в complex50 все вопросы отвечаемы.

Не считать автоматический `Step Recall` истинным без ручной проверки. Допускается LLM-as-a-judge с фиксированным шаблоном и контролем качества на ручной выборке; judge не должен видеть стратегию, для которой оценивает результат.

### Матрица сравнения

| Вариант | Retrieval | Расширение | Селектор | LLM |
|---|---|---|---|---|
| B0 | BGE-M3 | Нет | Relevance | Одинаковая |
| H1 | BGE-M3 | Пункт целиком | Relevance | Одинаковая |
| H2 | BGE-M3 | Подраздел | Relevance | Одинаковая |
| H3 | BGE-M3 | Ссылки + исключения | Protected coverage | Одинаковая |
| H4 | BGE-M3 | Адаптивно | Adaptive | Одинаковая |

Для H1–H4 логировать *все* изменения размера контекста. Сравнить варианты при фиксированном token budget и построить отдельную кривую качество/число токенов.

## 7. Критерии приёмки

1. Произвольный leaf chunk можно открыть как полный parent с сохранением точной страницы/абзаца; parser проходит тесты на переход страницы и списки.
2. Runtime не имеет доступа к gold QA и не содержит жёстких проверок на вопросы benchmark.
3. Gold-индексы из CSV/JSONL **не совпадают автоматически** с индексными chunk_id. Написать честный адаптер маппинга, аналогичный `scripts/evaluate_rag100.py`.
4. На 15 dev примерах H1 должен продемонстрировать, что дополнительно найденные положения не теряются; H2–H4 принимать только при измеряемом улучшении полноты без недопустимой потери точности и скорости.
5. Перед финальным выбором прогнать 35 test вопросов **без подбора параметров** и показать абсолютные метрики, paired deltas и bootstrap CI с учётом группировки по документу/процедуре.
6. Показать 10 вручную разобранных ошибок: какие leaf-кандидаты были найдены, какой parent добавлен, что исчезло на selection и что произвела LLM.
7. Существующий `rag100` не должен демонстрировать необъяснимой регрессии простых однофактных вопросов.
8. Итог — воспроизводимый config `hierarchical_parent`, отдельный toggle / feature flag, тесты, отчёт и результаты выбора `fast`, `balanced`, `quality` (не назначать победителя заранее).

## 8. Порядок работы агента по итерациям

**Первый коммит:** аудит ingestion и трассировок, контракт на `DocumentNode`, unit-тесты структуры, никаких изменений ранжирования.

**Второй коммит:** sidecar parent-map и `BGE + fixed parent`, dev-прогон с воспроизводимыми логами. Это минимальный жизнеспособный эксперимент.

**Третий коммит:** полноценный структурный parser PDF/DOCX и cross-references, проверка на документах с многостраничными пунктами.

**Четвёртый коммит:** adaptive selector и packing с token budget, отдельные абляции.

**Пятый коммит:** prompt и генерация инструкций с атрибуцией шагов к источникам.

**Шестой коммит:** end-to-end evaluation, error analysis, итоговое сравнение, документация и выбор режима по умолчанию.

После каждого этапа: список файлов, описание API и математической логики, тесты, реальные таблицы с dev-результатами, ошибки, latency/VRAM и список ограничений. Не отправлять коммиты в `main` без явного разрешения. **Начать с самого короткого работающего эксперимента Parent Expansion, а не полного переписывания ingestion.**
