# Эталонный датасет для проверки RAG по внутренним документам МФТИ

## Что создано

**100 вопросов**, из них **92 с ответом и подтверждением в документе**, **8 без подтверждённого ответа**. Разметка сделана на основе пользовательского `raw.zip`. Все 92 положительных примера имеют проверенный якорь `evidence_needle`, который **посимвольно присутствует** в извлечённом тексте соответствующей страницы PDF / абзаца DOCX. Сведения для эталонных ответов сопоставлены с соответствующими пунктами документа. Вопросы не являются реальными обращениями работников; они составлены для тестирования.

- `rag_gold_qa.jsonl`: основной машиночитаемый gold set, одна JSON-строка на вопрос;
- `rag_gold_qa.csv`: удобная плоская таблица, кодировка UTF-8 with BOM;
- `rag_gold_qa.xlsx`: книга Excel для ручной проверки, с листами вопросов, документов, инструкции;
- `corpus_units.jsonl`: извлечённые текстовые блоки с исходными координатами (страницы PDF, абзацы/строки таблиц DOCX) для тестов на уровне источников;
- `documents_manifest.json`: соответствие `Dxx` ↔ оригинальному имени, типу и статусу чтения;
- `evaluate_retrieval.py`: метрики поисковой части по JSONL с результатами.

## Структура строки JSONL

```json
{
  "id": "Q001",
  "split": "test",
  "question": "Как правильно отправить заявку в ИТ-поддержку МФТИ?",
  "reference_answer": "Через систему управления обращениями ... или на helpdesk@mipt.ru.",
  "answerable": true,
  "gold_document_ids": ["D09"],
  "gold_document_id": "D09",
  "gold_document_filename": "Приказ и Регламент работы первой линии техподдержки.pdf",
  "gold_location": {"type":"pdf_page", "page":2, "section":"п. 2.1"},
  "evidence_quote": "...",
  "evidence_needle": "приоритетный канал",
  "evidence_start": 1111,
  "evidence_end": 1129,
  "category": "ИТ-поддержка",
  "difficulty": "easy",
  "evidence_source": "native_text"
}
```

*Пример выше иллюстрирует формат: реальные цитаты и смещения следует читать из файла, а не из примера.*

- `gold_document_ids`: все допустимые документы с ответом. Для повторяющихся приложений **D14 и D05** учитываются как альтернативные источники на уровне выбора документа.
- `gold_document_id`: основной документ, по которому размечены точные координаты.
- `gold_location.page`: физическая страница PDF, начиная с 1; печатная нумерация внутри PDF может отличаться.
- `gold_location.paragraph`: порядковый номер абзаца в DOCX при извлечении `python-docx` (счёт с 1); **не номер страницы Word**.
- `evidence_needle`: дословный якорь на конкретной странице/в абзаце. `evidence_start` и `evidence_end` — символьные границы якоря в исходном `text` из `corpus_units.jsonl` (в Python UTF-8 строке, с конечной границей exclusive).
- `evidence_quote`: расширенный дословный фрагмент с контекстом, чтобы проверить смысл, но не обязательно весь пункт. Для вопроса, требующего нескольких положений, соседние пункты тоже важны.
- `answerable: false`: `gold_document_ids=[]`, ответ — просьба не выдумывать. Это **отрицательные** примеры, а не доказательство отсутствия информации во внешних ресурсах.

## Покрытие и ограничения

В исходном архиве **20 файлов**. Положительные примеры размечены по **11 документам**, которые удалось надёжно прочитать напрямую: четыре PDF с текстовым слоем и семь DOCX. Остальные документы остаются в исходном архиве, но **не имеют gold-примеров**. В частности, 5 PDF в значительной мере состоят из сканов (приказ об изменениях открытия ФЛС, электронная библиотека, бронирование концертного зала, поселение сотрудников, эксплуатация ЦОД); три XLSX — форматы и справочные таблицы. Также не составлены вопросы по шаблону DOCX приложения 1а. Эти источники требуют отдельного этапа OCR/контрольной вычитки и/или табличной разметки. **Не оценивайте покрытие всей базы как 100%**.

Для документов со множеством приложений, таблиц и возможных дубликатов (в частности, `D05` и `D14`) `gold_document_ids` содержит допустимые альтернативы, но эталонный `page`/`paragraph` размечен только для основного документа. Вопросы про 2025–2026 бюджетирование описывают **содержание исторических приказов**, не гарантируют актуальное требование для любой последующей даты.

Все положительные цитаты проверены автоматическим поиском точной подстроки в **извлечённом нативном тексте** с точной локацией. Это надёжная структурная проверка, но **не независимый юридический аудит**, не OCR-вычитка и не гарантия отсутствия иных действующих редакций. Отрицательные примеры подобраны явно вне содержания проверенных документов, но не могут строго доказывать отсутствие сведений в непрочитанных сканах.

## Как считать метрики retrieval

Для каждого вопроса прогоните ваш retriever по тем же исходным документам и сохраните `predictions.jsonl`:

```json
{"id":"Q001","retrieved":[{"document_id":"D09","unit_type":"page","unit_locator":2},{"document_id":"D18","unit_type":"page","unit_locator":3}],"abstained":false}
{"id":"Q002","retrieved":[{"document_id":"D09","unit_type":"page","unit_locator":2}],"abstained":false}
```

В `retrieved` нужно перечислить результат **в порядке убывания рейтинга**; `document_id` — из `documents_manifest.json`. Для chunk retrieval прикрепите исходный `page` (PDF) или `paragraph` (DOCX) к каждому своему чанку. Когда ваш чанк перекрывает несколько абзацев, в prediction следует добавить каждый подходящий `unit_locator` отдельно либо реализовать проверку пересечения диапазонов; текущий скрипт проверяет точное совпадение одной единицы.

```bash
python evaluate_retrieval.py rag_gold_qa.jsonl predictions.jsonl --split test
python evaluate_retrieval.py rag_gold_qa.jsonl predictions.jsonl --split dev
```

Скрипт считает:

1. **Document Hit@1/3/5/10** — найден ли один из допустимых документов в первых *k* выдачи.
2. **Document MRR@10** — среднее обратное положение первого релевантного документа.
3. **Source-unit Hit@1/3/5/10** — найдена ли точная размеченная страница или абзац (более строгая проверка; на другом чанкинге нужно адаптировать).
4. **Source-unit MRR@10** — обратный ранг точного источника.
5. **Abstention recall / accuracy** — только если все прогнозы содержат явное поле `abstained`; **не** оценивает семантическую точность текста ответа.

**Для генерации** отдельно вручную оцените correctness / faithfulness / citation precision. Автоматического строгого равенства между `reference_answer` и естественно-языковым ответом LLM быть не должно: перефразирование допустимо.

## Разделение данных

`dev`: **20** вопросов для настройки порогов, весов и гиперпараметров.

`test`: **80** вопросов для окончательного отчёта, на которые нельзя подгонять параметры. Генератор использует фиксированный seed 42 и сохраняет разнообразие ответных и неответных вопросов.

## Как проверить доказательства самостоятельно

1. Откройте вопрос и `gold_document_id` по `documents_manifest.json`.
2. В оригинальном PDF откройте физическую страницу `gold_location.page`; в DOCX найдите пункт `gold_location.section` и при необходимости сравните с абзацем из `corpus_units.jsonl`.
3. Сравните `evidence_quote` с документом. Поиск дословной строки `evidence_needle` должен подтвердить совпадение.
4. Для своей нарезки чанк–чанк сопоставьте фрагменты с `corpus_units.jsonl` через `document_id`, страницу, абзац или пересечение текста.
