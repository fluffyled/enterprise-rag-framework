## 6. Технические находки (полезны для эксплуатации)

- llama.cpp отклоняет JSON-схемы с union-типами (`["string","null"]`) → HTTP 400.
- `--parallel N` делит контекст на слоты `-c/N`: `-c 8192 -p 4` = 2048/слот;
  для verified-генерации нужно `-c 16384 -p 4` + символьные капы блоков
  (5800 суммарно / 2400 на блок: словесный счёт занижает BPE в ~2.4 раза).
- Несколько Retriever-инстансов в одном процессе на 8 ГБ VRAM → деградация
  до минут на вопрос. Один прогон = один процесс.
- `/health` llama-server отвечает до загрузки модели — readiness проверять
  тестовой генерацией.
- Очереди прогонов обязаны убивать llama-server до и после (`taskkill //F //IM`),
  иначе сироты конкурируют за GPU (был случай: 4 сервера, p95 взлетел в 30×).
- llama-server готовность: поллинг генерации, не /health.

## 7. Ограничения исследования

- Один LLM (Qwen2.5-3B); oracle-потолок текущей связки ~0.64 Step Recall —
  следующий рычаг: модель 7B–14B (не влезает в 8 ГБ VRAM; кандидат — Kaggle
  для публичных датасетов).
- H5: 14% ложных отказов, медленная генерация; формулировки фрагментарные.
- H3/H4: 9 с/вопрос; planner fallback на 18/50 вопросах (корректно для простых).
- Один аннотатор ручных проверок; n=50/74/200 — выводы опираются на CI и
  согласованность по корпусам.
- Enrichment-эффект оценён на одном корпусе; инфраструктура готова к пересмотру.
