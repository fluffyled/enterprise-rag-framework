# Retrieval v3 — оптимизация Coverage-Aware Retrieval

Платформа: RTX 3070 Ti Laptop, torch 2.11.0+cu126, CUDA-индекс внутреннего корпуса
(3079 фрагментов, fingerprint `a0b27b50…`). Все абляции на holdout (27 вопросов,
24 отвечаемых) — диагностический сплит; на нём уже выбиралась архитектура V2.
Окончательная оценка — на независимом test split (этап 6).

Парные сравнения по одинаковым вопросам; метрики считаются по итоговому
selected context (top-6), gold spans только в offline-оценке.

## 3.1 Декомпозиция вопросов

**D0 (existing rules) — оставить.** Эталон: ER@6 0.8681.

**D1 (improved rules) — отклонено.** На ручной разметке (20 вопросов, exact-match)
D1 давал 20/20, но end-to-end на holdout потерял holdout-017 (1.0 → 0.667):
вопрос с условной клаузой («…, когда …») D1 разрезал на 3 подзадачи, и отдельный
проход по условию вытеснил доказательство третьего требования. Консервативный
разрез D0 сохраняет контекст условия. Других изменений нет → польза не показана,
риск регрессий есть. Отрицательный результат зафиксирован.

**D2 (local LLM planner) — отклонено.** Planner реально работал (27/27 запросов,
fallback не срабатывал, constrained JSON валиден), но выдача совпала с D1
(те же 0.8542) при медиане 1.514 с против 0.167 с (9× медленнее, p95 3.24 с).
Стоимость дополнительного вызова Qwen на CPU/GPU не окупается: качество
декомпозиции planner'ом не превосходит правила ни на ручной разметке, ни end-to-end.

## 3.2 Coverage Selection

- **Greedy с нормировкой по токенам и λ=0.15 (stable) vs голый greedy** —
  идентичные результаты на holdout. Нормировка безвредна; оставлена как есть.
- **Обязательный min-subtask** — идентичные результаты (на holdout у всех
  ошибочных вопросов селектор и так берёт фрагмент подзадачи). Оставлено выключенным:
  жёсткое требование не нужно, а на других данных может вредить.
- **Document diversity 0.05 — отклонено, вредно**: ER@6 −0.18 (0.6875).
  Подтверждено предупреждение плана: у части вопросов все доказательства в одном
  документе, принудительное разнообразие вытесняет нужные фрагменты
  (uniq_documents 5.56 против 2.63 при той же норме).

## 3.3 Token budget

Бюджет 1000/2000/3000/4000 даёт **идентичные метрики**. Средний итоговый контекст
≈ 640 токенов — запас бюджета большой, ограничением бюджет не является.
Это согласуется с аудитом ошибок (Insufficient Context Budget = 0).
Адаптивный бюджет не внедрялся: анализ ошибок не дал оснований.

## Candidate pool (candidate_top_k)

**20 → 40: отклонено после внешней валидации.** На holdout: ER@6 0.8681 → 0.8958
(+0.028, лучший результат серии), MRR +0.005; AEH@6 без изменений. Стоимость:
медиана 0.167 → 0.245 с. Однако на MultiDoc2Dial (300 запросов) — значимая
регрессия Doc Recall@5 −0.037 [95% CI −0.070…−0.007] (6/17), ER@6 −0.03.
Механизм: на одно-требовательных вопросах пул 40 размывает RRF-ранг gold-документа
и coverage выбирает лишние фрагменты. Противоречивые данные → пул оставлен 20.

## 3.4 Эффект batch_cross_encoder (этап 4, качественная часть)

Качество — побайтово идентично stable (batched forward даёт те же скоры
в пределах float32). По этапу reranking: медиана 0.053 с в обоих вариантах,
mean 0.157 → 0.107 с (−32%), p95 total 0.852 → 0.643 с. На GPU выигрыш скромный
(miniLM и так быстрый), но хвост режется — принято как компонент V3-P.

## Решение по конфигурации

**Принято (V3-Final):** `configs/retrieval_v3_final.yaml` = stable coverage +
batch_cross_encoder + FastBM25, `candidate_top_k: 20` — то есть качество строго
равно V2 при улучшенной latency. См. 06_final_comparison.md.

**Отклонено после внешней валидации:** расширение пула до 40 кандидатов.
На диагностическом holdout дало лучший ER@6 (0.8958), но на MultiDoc2Dial (300
запросов) — значимую регрессию Doc Recall@5 −0.037 [95% CI −0.070…−0.007],
6 улучшено / 17 ухудшено: на одно-требовательных вопросах большой пул размывает
RRF-ранги gold-документа. Данные с противоположными выводами на разных корпусах
→ не внедряем (принцип: не усложнять без подтверждённой необходимости).

D1/D2/diversity отклонены ранее (см. выше). Бюджеты и min-subtask — нейтральны.
