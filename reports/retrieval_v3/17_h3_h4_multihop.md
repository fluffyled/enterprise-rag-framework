# Итерация D — Question Decomposition + Multi-Hop Retrieval (H3/H4)

Гипотеза: разложение вопроса на требования и отдельный поиск по каждому
покроет многокомпонентные процедурные вопросы лучше, чем одиночный поиск.

## Реализация

`navigator/multi_hop.py` (флаг `multi_hop`, `multi_hop_rounds`):
1. План: `local_llm_decompose` (Qwen, constrained JSON, extractive-проверка с
   восстановлением смещений — исправлен баг, при котором планировщик молча
   откатывался на правила из-за неточных offset'ов модели).
2. Поиск по исходному вопросу + каждому подвопросу (BGE-M3 + BM25 + reranker
   на каждый), объединение с записью, какой подвопрос нашёл доказательство.
3. Покрытие требований: supported/unsupported по скору reranker.
4. H4: второй раунд целевого поиска по неподдержанным (не сработал — порог
   слишком лоялен, см. ниже).
5. Иерархическое расширение (H1) итогового объединённого набора.

## Результаты (complex50, чистый прогон, planner 32/50 + fallback 18, среднее 3.1 подзадачи)

| Конфиг | Clause Recall | All Found | Step Recall | Complete@all | False Abst | Контекст | Retrieval мед. |
|---|---:|---:|---:|---:|---:|---:|---:|
| Q0 baseline | 0.759 | 42% | 0.461 | 8% | 6% | 658 ток | 2.3 с |
| H1 parent | 0.914 | 68% | 0.426 | 10% | 4% | 1792 ток | 2.0 с |
| **H3 multi-hop** | **0.925** | **76%** | **0.306** | 4% | 0% | 3050 ток | 8.9 с |
| **H4 iterative** | **0.927** | **78%** | **0.360** | 4% | 0% | 3056 ток | 9.3 с |
| O1 oracle | 1.000 | 100% | 0.636 | 14% | 2% | 227 ток | — |

## Интерпретация

1. **Retrieval достиг потолка**: 0.925–0.927 clause recall при all-found 76–78%
   — почти oracle (1.0). Дальше улучшать поиск по этому корпусу почти нечего:
   остаток — 2 непарсируемых места (NM_para63) и редкие промахи кандидатов.
2. **Генерация деградирует с ростом контекста — количественно**:
   Step Recall 0.46 (Q0, 658 ток) → 0.43 (H1, 1792 ток) → 0.31–0.36
   (H3/H4, 3050 ток). Трёхкратный рост контекста не компенсируется ростом
   покрытия: модель выбирает предложения хуже. Это не «больше данных помогут»,
   а «модель тонет в контексте».
3. **H4 == H3 фактически**: второй раунд не запустился ни разу — порог
   supported (rerank score > −2.0) лоялен, всё помечено supported.
   Итеративное восполнение в текущей форме не работает (зафиксировано
   как отрицательный результат, не подгонял порог под данные).
4. Планировщик реально работает (32/50), fallback — на вопросах без явной
   составности. 18 fallback'ов — ожидаемое поведение для однотребовательных.

## Вывод итерации D

Multi-hop принят как retrieval-компонент для сложных вопросов (лучшее
покрытие), но **не как конфигурация по умолчанию**: цена — 4× latency и падение
качества ответа при текущей генерации. Критерий ТЗ «польза на смешанном
наборе» — не достигнут из-за генерации. Приоритет окончательно смещён на H5:
структурированные evidence blocks + проверяемая генерация, где модель ссылается
на блоки по ID, а не выбирает предложения из потока текста.
