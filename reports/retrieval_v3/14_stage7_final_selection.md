## Выбранные конфигурации

### Fast — `configs/retrieval_cuda_baseline.yaml` (E5 + FastBM25, top-k)

Решение по требованию плана сравнить с E5 baseline явно: на основном корпусе
(rag100) B0 имеет лучшие ранговые метрики среди E5-вариантов (Unit MRR 0.805
против 0.688 у V3-Final) и лучший E2E success (0.840), при минимальной задержке
(0.39 с retrieval / 0.84 с end-to-end). V3-Final выигрывает только на
многотребовательном CUAD (0.2597 vs 0.1588) — если профиль вопросов смещён
в сторону составных юридических, V3-Final предпочтительнее; для текущего
корпуса (преимущественно однофактовые вопросы) — B0.

### Quality — `configs/retrieval_bge_adaptive_rerank.yaml` (BGE-M3 + bge-reranker-v2-m3 + adaptive)

Качество максимально везде: CUAD 0.4571 (лучшее), mdb 0.7300 (лучшее),
rag100 0.857 без регрессий, E2E 0.870 (лучшее у rerank-конфигураций).
Adaptive-часть бесплатна по качеству и снижает latency на однофактовых
вопросах (0.79 с против 1.08 с у статического rerank — экономия на coverage-
матрице для 85% вопросов). Диагностика выбора стратегии включена.
Более простая альтернатива — `configs/retrieval_bge_rerank.yaml` (тот же
уровень качества в пределах шума).

### Balanced — `configs/retrieval_bge_adaptive.yaml` (BGE-M3 + mMiniLM + adaptive)

Компромисс: CUAD 0.3566 (+0.144 к E2, значимо), rag100 0.858 без регрессий,
mdb 0.6600, задержка 0.41 с — вдвое дешевле rerank-вариантов по VRAM
(без bge-reranker: ~2 ГБ против ~4.5 ГБ) и в 2.5 раза быстрее.
Подходит как конфигурация по умолчанию для продакшена с непредсказуемым
смешанным потоком вопросов.

## Универсальность (требование «не подгонять под rag100»)

Каждое принятое изменение проверено на ≥3 корпусах (rag100, CUAD, MultiDoc2Dial)
и отклонено, если выигрыш ограничивался одним датасетом: pool-40 (регрессия
на mdb), plain coverage на однофактовых (значимое падение рангов), protected
поверх сильного reranker'а (нет эффекта). Отрицательные результаты сохранены
в отчётах 09–11.

## Рекомендации по интеграции

1. Продакшен-конфиг по умолчанию: Balanced (`retrieval_bge_adaptive.yaml`).
2. Для задач максимального качества (юридические/многотребовательные):
   Quality (`retrieval_bge_adaptive_rerank.yaml`).
3. Ресурсно-ограниченный сценарий: Fast (`retrieval_cuda_baseline.yaml`).
4. Дальнейшее развитие — генерация (главный класс ошибок, этап 6):
   калибровка отказов, полнота цитат, более сильный judge.
