# AUDIT_REPORT — аудит и исправление измерений Hierarchical RAG

Дата: 2026-11-14. База: `abe0c6c`. Цель — корректная, воспроизводимая,
независимая от gold оценка; алгоритмы, веса моделей, гиперпараметры retrieval
и тестовые вопросы НЕ изменялись ради метрик. 90/90 тестов (6 новых
демонстрируют прежнее завышение).

## 1. Найденные дефекты и исправления

### D1. Clause Store строился только по gold-документам — ЗАВИСИМОСТЬ ОТ GOLD
- **Где:** `scripts/build_clause_store.py` (фильтр `needed = {gold filenames}`).
- **Суть:** «структурный парсер» молча ограничивался 8 документами из разметки
  complex50; остальные 12 документов корпуса не получали clause-представления.
  Runtime-поиск при этом читал store корректно, но сам артефакт был подогнан
  под бенчмарк.
- **Исправление:** store строится по ВСЕМ документам `source_documents.json`;
  gold используется только для offline-валидации покрытия цитат.
- **Результат:** 439 → **747 clauses, 20/20 документов**; для 8 gold-документов
  clauses побайтово совпадают с прежними (парсер от gold не зависел — зависел
  только фильтр). Baseline старого store сохранён:
  `data/clauses/clauses_goldscoped_baseline.json`. Отчёт постройки:
  `data/clauses/clause_build_report.json` (в т.ч. 2 XLSX без нумерованных
  пунктов — ожидаемо; дубликаты номеров в основном от перезапуска нумерации
  в приложениях — задокументировано, на метрики не влияет: оценка по spans).

### D2. Clause Recall засчитывал совпадения в ЧУЖОМ документе
- **Где:** `scripts/evaluate_complex_rag.py:stage_coverage` (прежний needle-match
  без проверки документа).
- **Суть:** needle искался в контенте любой стадии; в корпусе есть дубликаты
  положений (D05/D14 — предупреждение самого датасета), поэтому «покрытие»
  могло засчитываться за текст в дублирующем документе.
- **Исправление:** совпадение засчитывается только в контенте документа
  gold evidence. Минимальный пример: `tests/test_audit_metrics.py::
  test_cross_document_needle_match_is_not_coverage` (legacy засчитывал 1.0,
  новая метрика — 0.0).

### D3. strict/soft совпадения слиты в одну метрику
- **Исправление:** отдельно `clause_recall_strict` (дословный needle),
  `clause_recall_soft_only` (токенное пересечение с цитатой ≥ 0.5) и их
  объединение `clause_recall`. Аналогично `fact_coverage_strict`.

### D4. Step Recall завышался полными цитатными блоками H5
- **Где:** `generation_metrics` — оценка по `quote` шагов; для H5 цитата =
  полный текст блока-пункта, который ТРИВИАЛЬНО содержит evidence.
- **Суть:** шаг с посторонним действием, цитирующий правильный блок, получал
  засчитывание факта. Пример завышения:
  `tests/test_audit_metrics.py::test_step_recall_not_inflated_by_full_block_quote`
  (legacy 1.0 → новая 0.0).
- **Исправление:** для verified-режима оценивается СОДЕРЖИМОЕ шага
  (action+actor+condition+deadline) против объединения ВСЕХ обязательных
  evidence факта (цифры ⊆, ≥50% содержательных слов). Составные факты
  требуют покрытия всех evidence — тест
  `test_composite_fact_requires_all_evidence`.

### D5. Ошибки генерации смешивались с отказами
- **Исправление:** отдельные `error_rate` (status=error) и `false_abstention`
  (status=insufficient). Тест `test_error_separated_from_abstention`.

### D6. H5 не сохранял реальные идентификаторы
- **Где:** `navigator/verified_answer.py` — блоки имели только позиционный
  `block_N`.
- **Исправление:** блоки и шаги несут `chunk_id`, `clause_id`, `document`,
  `clause` из метаданных индекса/clause store.

### D7. Механизм `supported` в H4 фактически отключён + стадии multi-hop смешаны
- **Где:** `navigator/multi_hop.py`, `SUPPORTED_SCORE = -2.0`.
- **Суть:** при таком пороге supported≈всегда → раунд-2 H4 не срабатывал
  (ранее зафиксировано как «H4 ≡ H3»); дополнительно стадии rrf/reranked
  в traces multi-hop прогонов относятся только к базовому вопросу, что
  позволяло ошибочно читать их как покрытие подзадач.
- **Исправление (минимальное, без подгонки):** порог вынесен в константу с
  документированным дефектом; в диагностику добавлены `support_threshold`,
  `candidate_ids`; в evaluator стадии multi-hop прогонов переименованы в
  `base_rrf`/`base_reranked`. Порог НЕ менялся, т.к. его калибровка — это
  настройка под данные.

## 3. Выводы: что подтверждено, что пересматривается

**Подтверждено:**
1. Весь retrieval-блок: H1 parent expansion и H3/H4 multi-hop значимо поднимают
   документ-специфичное покрытие (0.707 → 0.896–0.909, strict 0.845);
   остаток до oracle — 2 непарсируемых места + редкие hard-кейсы.
2. Потолок задан генерацией: oracle-контекст + verified-генерация = 0.576
   Step Recall — сильнее текущей связки на большом контексте не выжать.
3. Обычная генерация деградирует на длинных контекстах (подтверждено ранее,
   не зависело от исправленных метрик).

**Пересматривается:**
4. **Заявка «H5 — лучшая полнота ответов (0.558)» была завышена дефектом D4.**
   При оценке СОДЕРЖИМОГО шагов H1+H5 даёт 0.426 — на уровне baseline (0.453,
   разница в пределах шума n=50), Complete@all 10% против 8%. Реальные
   преимущества H5 — не полнота, а: детерминированно проверяемые ссылки
   (каждый шаг с пунктом-источником), явный список недостающего вместо
   домысливания, и потолок на идеальном контексте (O1+H5: Step 0.576,
   Complete 26% — лучший честный результат исследования).
5. Оценка unsupported для H5 (0.42) завышена в обратную сторону: плановые шаги,
   которых нет среди 224 gold-facts, но которые корректны как промежуточные
   действия процедуры, считаются unsupported. Метрика сопоставима только
   внутри одного режима.

**Итог аудита:** направления выводов сохранились (retrieval улучшен и
подтверждён; генерация — bottleneck), абсолютные значения стали честнее:
H5 перестаёт быть «революцией полноты» и занимает своё место как режим
проверяемости и явных отказов; главным качественным лидером честной матрицы
является сочетание насыщенного retrieval (H4) с более сильной LLM —
направление G-экспериментов.
